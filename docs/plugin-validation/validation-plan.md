# Android 实验与性能验收

- 状态：页面指标已测；MuMu 真实普通聊天、输入插件、Remote 续聊和双模式隔离通过，真实中文键盘仍有环境限制。
- 维护角色：DSH Mobile 项目协作 Agent。
- 最近核验：2026-09-22。
- 依据：[服务契约](./local-services.md)、用户关心原生上限与插件兼容成本。

## 运行验收

| 场景 | 操作 | 通过证据 |
| --- | --- | --- |
| 独立普通聊天 | 电脑 DSH/中继不可用时，手机真实请求模型并停止、重新进入历史 | 真实 API 回复、流式状态、重启读回一致；Key 不进入页面/日志 |
| 真实主题与 locale | 修改设置、切换主题、重启、停用重启用插件 | CSS、状态、设置持久化和清理均正确 |
| 安装包插件样例 | 通过原 ModuleLoader 加载 fixture-live-client，操作配置卡、overlay，然后卸载重装 | 渲染真实、计数/监听不重复、CSS 与 contributions 释放 |
| 输入增强 | 中文输入法、选提示词、改 draft 后处理旧候选、移除 source | 不覆盖新草稿，不留订阅或旧菜单 |
| Host 插件边界 | 普通模式尝试依赖电脑的插件/能力 | 明确不可用或引导切换，不假成功、不自动执行电脑任务 |
| 双模式隔离 | 实际两个环境注入独有哨兵、跨环境读取和原生桥调用 | 对方数据不可读，错误来源不可调用桥；正常各自请求仍可用 |
| Android 生命周期 | 切后台、恢复、进程回收与重启 | 历史一致，未完成请求标记中断，写操作不自动重放 |

## 对照方法

固定 DSH commit、插件版本、release/debug 类型、WebView 版本、设备型号、Android 版本、刷新率和数据集；记录冷启动/热启动、至少三次重复的中位数与最差值。真机和模拟器分开报告。网络模型耗时与界面渲染耗时分开，不把模型延迟算作 WebView 开销。

组合 A：相同聊天 renderer，关闭可选插件；组合 B：开启主题/设置页/输入样例等代表性插件。两组采用相同预生成普通聊天记录与相同分片回放，再单独执行真实模型测试。合成数据可以测性能，不能替代模型连通性验证。

## 当前性能验收

2026-09-22 用户明确性能不用过于严格，FCP/LCP/CLS/TBT 在合理区间即可。当前以页面启动与明显交互问题为重点；目标真机、严格内存/帧率、5,000 条大型数据集压力测试移至后续可选，不再阻塞第四步。安全、真实模型与历史正确性仍按功能标准验收。

参考 [FCP](https://web.dev/articles/fcp) ≤1.8 秒、[LCP](https://web.dev/articles/lcp) ≤2.5 秒、[CLS](https://web.dev/articles/cls) ≤0.1、[TBT](https://web.dev/articles/tbt) 约200毫秒以内的良好目标。它们是优化参考，不是将一次轻微波动自动判为项目失败的苛刻门槛。至少三次记录中位数/最差值；实验数据不冒充线上用户 p75。

- `npm run measure:page`：Lighthouse 13.5.0、独立 Edge profile、移动视口、loopback 资源、无额外 CPU/网络节流。每次清理该临时 origin 的存储，得到标准导航 TBT；不清理用户 App 数据。
- `DSHM_ANDROID_SERIAL` + `node scripts/measure-android-page.mjs`：实际 APK 本地资源的 FCP/LCP/CLS；PerformanceObserver 采集到页面 ready 后两秒，保留原始长任务，但不冒充 Lighthouse TBT。是 MuMu 页面 reload，非 Activity 冷启动。
- 两组由 `?optional-plugins=off/on` 控制主题与上游样例是否实际进入模块图；基础 Modules/locale/renderer、原输入插件和普通聊天页面仍相同，不声称完全没有插件。
- 测量不调用模型；真实网络首字延迟、停止与流式下插件交互另行验证。

## 后续可选的深入测量

| 项目 | 方法与记录 |
| --- | --- |
| 包体 | release APK 文件字节、按 ABI 配置、安装后 app/data/cache 占用分别记录 |
| 冷/热启动 | Activity 启动时间、页面首次可交互、插件 ready 三个时间点，不混为一个指标 |
| 长聊天 | 100/1,000/5,000 条文本与代码块记录；固定滑动脚本，记录帧时间与卡顿比例 |
| 持续输出 | 相同 30/60 次每秒分片回放；记录每秒渲染提交、长任务、输入响应，另验真实 API |
| 键盘 | 聚焦、弹出/收起、中文组合输入、返回手势；记录遮挡、滚动位置、输入到下一绘制耗时 |
| 插件生命周期 | 首次加载、启用/停用重复 20 次；记录时间、残留 style/listener/slot 和内存趋势 |
| 内存 | adb dumpsys meminfo + WebView renderer 进程，空闲/长列表/流式/卸载后分别采样；不只统计 Activity 进程 |
| 数据隔离 | 功能通过/失败独立记录，不用性能平均值掩盖隔离失败 |

以上深入测量不是当前完成条件；若以后开展，再固定目标设备、负载和采样方法。不能把未运行的项目记为通过，也不继续要求用户提供真机才能推进本阶段。

## 如何形成外壳结论

首个技术载体只用于测 DSH Web 运行环境，不等于最终选型。相同 Web renderer 的主要成本不会因 Capacitor 换为 Kotlin 壳自动消失。若瓶颈位于 JS/DOM，应先定位并优化渲染与插件；若位于键盘、网络桥、生命周期，再比较外壳方案。报告结论需包含证据、已排除的原因和剩余代价，不预设一定选择某个框架。
